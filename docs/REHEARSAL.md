# 반복 리허설 운영

## 사용 방법

- 기존 주소 `https://teuksae-hyeonjangpan-v2.vercel.app/`를 새로고침합니다.
- 서버의 `REHEARSAL_ENABLED=true`이며 2026-10-05 00:00 한국 시간 전이면 리허설 배너가 표시됩니다.
- 상단에서 여섯 행사일의 콘텐츠를 선택할 수 있습니다. 현황 갱신 시각과 사진 참여 수는 실제 입력 시간/한국 날짜 기준입니다. 시계나 실제 날짜를 바꾸지 않습니다.
- 기도·묵상·사진 접수 → 최고 관리자 검토 → 공개 승인/반려 → 작성자 철회 또는 관리자 삭제를 실제 서버로 연습할 수 있습니다.
- 승인한 리허설 글/사진도 해당 링크에 접속한 사람이 볼 수 있습니다. 가상 문구와 비식별 이미지만 사용합니다.
- `/admin`의 기존 아이디/비밀번호를 사용합니다. 리허설용 계정은 설치 시 한 번 복제되며 이후 실제 운영 계정과 분리됩니다. 리허설에서 계정을 변경해도 실제 운영 계정은 바뀌지 않습니다.
- 최고 관리자에게 `리허설 데이터 초기화`가 나타납니다. 확인 문구 `리허설 초기화`를 입력한 뒤 삭제를 확정하면 다시 시작할 수 있습니다.
- 초기화는 리허설 게시물·현황·운영 이력만 대상으로 합니다. 계정/로그인과 각 기기의 개인 메모/다운로드 파일은 유지합니다. 사진은 즉시 비공개 처리되며 비공개 저장소의 잔여 파일은 시간별 정리 작업이 순차 삭제합니다.
- 다른 기기에서 이미 열어 둔 화면은 새로고침합니다. 초기화 이전 현황을 저장하려 하면 버전 충돌로 보호됩니다.

## 실제 행사 전환

2026-10-05 00:00 KST에 서버가 자동으로 원래 live namespace로 돌아갑니다. 리허설 로그인은 실제 운영에서 유효하지 않으므로 다시 로그인합니다. 기존 실제 운영 데이터와 계정은 그대로 유지됩니다. 리허설 데이터를 실제 행사로 복사하지 않습니다.

`REHEARSAL_ENABLED=true`는 행사 후에도 정리 작업이 rehearsal 저장소를 계속 청소할 수 있도록 유지합니다. 이 값이 true라도 서버 시간 경계 이후에는 리허설 모드로 진입할 수 없습니다. URL 파라미터와 기기 시계로 리허설을 켤 수 없습니다.

## 설치/검증

1. `node scripts/build-rehearsal-migration.mjs --check`.
2. Supabase SQL Editor에서 `supabase/migrations/009_rehearsal.sql`을 **한 번만** 실행합니다. 전체는 단일 트랜잭션이고, 이미 rehearsal namespace가 있으면 거절합니다.
3. 이어서 `010_rehearsal_reset_safeupdate.sql`을 실행합니다. Supabase API의 `pg_safeupdate` 호환성이 필요합니다. SQL Editor에서 reset 성공만으로 API 성공을 판단하지 않습니다.
4. Vercel Production 환경에 `REHEARSAL_ENABLED=true`를 추가하고 배포합니다.
5. `/api/status`의 `rehearsal:true`, 분리된 13개 현황, admin 로그인을 확인합니다.
6. 가상 기도/묵상/사진 제출, pending 비공개, 승인 공개, 반려/철회/삭제, 현황 저장/충돌, 초기화를 검증합니다.
7. 실제 `ops_*`, `community_v2_*`의 업무 데이터가 바뀌지 않았는지 별도로 확인합니다. 정리 cron의 `last_cleanup_at` 메타데이터는 자연적으로 바뀔 수 있습니다.

DB 회귀: `PGLITE_MODULE=<installed @electric-sql/pglite/dist/index.js> node tests/scripts/rehearsal-db.mjs`.
일반 회귀: `npm test`, `npm run test:server`, `npm run lint`, `npm run build`.

## 안전 경계

- 실제/리허설 RPC·테이블·인덱스·락·스토리지 버킷을 분리합니다. 브라우저 삭제 영수증/묵상 초안/도장 키도 분리합니다.
- 공개 상태 응답은 `no-store`입니다. 행사 전환 전에 캐시된 리허설 정보가 이후 실제 현황으로 재사용되지 않습니다.
- 커뮤니티 쓰기는 UI가 받은 namespace 헤더와 서버의 현재 mode가 일치해야 합니다. 자정 전부터 열린 리허설 화면이 실제 행사에 글을 잘못 제출하지 않습니다.
- 초기화는 최고 관리자 세션/역할을 DB에서 다시 확인하고 전역 배타 락으로 리허설 변경과 직렬화합니다. 자원 버전을 증가시키고 삭제 영수증/업로드 tombstone을 보존합니다.
- migration 001의 과거 `/app`는 현재 Companion root와 별개입니다. 해당 구형 경로의 리허설 전환을 주장하지 않습니다.
