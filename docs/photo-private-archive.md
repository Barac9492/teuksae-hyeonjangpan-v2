# 관리자 사진 비공개 보관 (로컬 준비)

관리자 `사진 승인`에서 확인한 사진을 선택해 **선택 비공개 보관**할 수 있다. 공개 중인 사진도 즉시 서버의 공개 목록/이미지 조회 대상에서 제외하고, 저장된 사진 파일과 메모는 유지한다. `검토 상태 → 비공개 보관` 목록에서 확인하고 **선택 검토 대기로 이동**하면 비공개 대기로 돌아간다. 다시 내용을 확인하고 승인해야 공개된다.

- 사진 전용, 최고 관리자만 가능. 업로더 측 새 보관 옵션은 없다. 제출자의 기록에는 `관리자 비공개 보관 중`을 표시하고 기존 철회·삭제 권한을 유지한다.
- 반려는 내용·사진 제거, 휴지통은 복원 가능한 삭제, 보관은 검토 화면의 별도 비공개 유지 상태다. 보관에서 휴지통 이동/영구 삭제 및 기존 API의 반려가 가능하다. 휴지통 복원도 대기로만 돌아간다.
- 준비 완료된 대기/공개 사진만 보관한다. 원본이란 기존 저장소에 보관된 정규화 PNG이며, 업로드 전 파일이나 제거된 EXIF를 복원하지 않는다.
- 기존 공개 동의, payload/token 해시, 원본 경로, 날짜, ready 값은 유지한다. 보관이 공개 동의나 새 승인을 대신하지 않는다. 보관 사진은 기존 `pending/approved` 기준의 오늘 사진 참여 건수에서 제외된다.
- 보관 기한을 새로 약속하거나 정리 정책을 바꾸지 않는다. 제출 철회·영구 삭제·반려와 기존 파일 정리 경로를 유지한다. 준비 완료된 보관 파일은 미완료 업로드 정리 대상이 아니다.

## 서버와 DB 경계

`20261004215412_photo_private_archive.sql` 한 개가 필요하다. 기존 status CHECK에 `archived`를 추가하고, `archived`는 준비 완료/경로가 있는 사진만 허용하는 CHECK를 추가한다. `community_v2`만 교체한다. 새 테이블·컬럼, 기존 데이터 변환, Storage 변경, 권한 확대는 없다. 이미 배포된 기도 가림 로직은 그대로이며 미배포 기도 직접 편집 기능은 포함하지 않는다.

- 기존 session/account 재검증·advisory/row lock·expectedVersion 검사를 사용한다. archive/unarchive는 한 번만 상태·버전·처리자 감사 기록을 변경한다. 같은 이전 버전 재시도는 409로 실패하므로 결과 확인 후 새로 선택한다. 응답 유실을 성공으로 추정하지 않는다.
- 선택 작업은 현재 페이지의 명시적 선택 ID/버전만 순차 처리한다. 409는 해당 건 실패로 기록하고 계속, 인증·통신·응답 오류는 나머지 처리를 중단한다. 결과 및 새 목록을 보여주고 선택을 해제한다. 페이지·필터·탭 이동은 선택을 유지하지 않는다.
- 공개 legacy list와 12건 public page는 이미 `status='approved'`를 LIMIT 전에 적용한다. 보관 상태는 양쪽에서 제외된다. 직접 이미지 API는 익명 404, 일반 팀 계정 403, 재검증한 최고 관리자만 200이다. Storage는 private이며 signed/public URL을 발급하지 않는다. 이미지 body를 전부 받은 뒤 DB 상태를 다시 확인해 도중 보관된 파일의 전송을 막는다.
- JSON과 이미지 응답은 `private, no-store`, `Vary: Cookie, Origin`을 유지한다. 서비스 워커는 `/api/`를 캐시하지 않는다. 공개 콘텐츠의 별도 서버 캐시/메타데이터/내보내기 경로는 없다. 업로더의 로컬 파일 저장 기능은 자신의 파일을 처리한다.
- 이미 내려받거나 화면에 그린 사본은 회수할 수 없다. 열린 공개 화면은 기존 foreground 30초 확인/재진입/연결 복구 때 목록이 갱신되며, 오프라인·백그라운드·조회 실패 때 이전 피드를 숨기는 동작을 유지한다. 기존 캐시 헤더 준수 범위를 넘어 외부 캐시/사본의 즉시 삭제는 보장하지 않는다.

## 호환성과 배포 제안

1. 별도 PR/배포 승인 후 최신 main과 운영 DB 스키마/함수 정의가 기준과 맞는지 **본문 조회 없이** 확인한다. 적용 이력의 기도 가림 migration 이름이 로컬과 다를 수 있으므로 이름만으로 재적용하지 않는다.
2. 추가 마이그레이션 한 개를 먼저 적용한다. 기존 목록·승인·삭제 계약은 유지한다. 구 앱은 보관 항목을 기본 관리자 목록에서 받지 않으며, 오래된 승인 요청도 DB에서 차단된다. 구 업로더 화면은 새 상태 문구를 몰라 상태 확인 오류를 보일 수 있으므로 새 앱으로 새로고침한다.
3. 이 브랜치의 API/UI를 배포한다. 새 UI는 `archiveSupported`가 없으면 보관 버튼을 비활성화하고, API의 보관 필터는 구 DB 응답을 503으로 거절한다. 배포·검증 자체가 실제 사진의 상태를 변경하지 않는다.
4. 롤백은 앱만 되돌리고 DB의 추가 상태/함수를 유지한다. 보관 행이 생긴 뒤 status CHECK나 이전 RPC로 되돌리지 않는다. 기존 서버도 승인 상태 검사를 사용하므로 이미 보관된 사진은 계속 비공개다. 새 body-read 후 재검증 강화는 새 서버에서 제공된다.

이번 작업은 로컬 구현·합성 검증만 수행한다. PR, 운영 DB 적용, 배포 및 실제 사진 보관은 수행하지 않았다. 별도 미배포 기도 브랜치 `12a7deb94dd41d87594327dff40853b62f738411`는 보존한다.
